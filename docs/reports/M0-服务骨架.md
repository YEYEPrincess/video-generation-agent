## 3. 关键设计决策

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| D-1 | 队列与存储**同一张 SQLite**，不引入 Redis | 3 天内少一个组件 = 少一个演示失败点；`enqueue/lease/heartbeat/reclaim` 四个方法抽干净，换 Redis 只改 `queue.py` | 无跨机器能力，README 需注明 |
| D-2 | 抢锁用**单条** `UPDATE … WHERE status='PENDING' … RETURNING *` | SQLite 单语句原子；不需要显式锁、不需要先 SELECT 再 UPDATE（那会读写升级） | 依赖 SQLite ≥ 3.35（实际 3.53） |
| D-3 | 时间戳**双轨**：`lease_until` 用 epoch 秒，展示字段用 ISO8601 | 租约比较是数值比较，不受时区/格式影响；ISO 便于人读和排障 | 两套表示，需在 `db.py` 收口 |
| D-4 | 幂等键纳入 `STAGE_CONFIG_VERSION` | 改 prompt / 换模型必须让下游失效，否则「改了 prompt 但产物没变」会让人怀疑人生 | 每次改 prompt 要手动 +1（已写进注释） |
| D-5 | `StageResult.validate_contract` 开关 | M0 假产物不是真契约，硬校验会误报；但开关**显式写在 handler 上**，真实阶段必须为 True | 一个可能被滥用的开关，靠 code review 兜 |

## 5. 实现过程中遇到的 3 个真实问题（可做面试素材）

### 问题 1：心跳续租后租约时间没有变

- **现象**：`test_heartbeat_and_finish` 断言 `after > before` 失败，两个值在小数点后 7 位完全相同。
- **根因**：Windows 的 `time.time()` 实际粒度约 15.6ms，`lease()` 与 `heartbeat()` 落在同一个 tick 内。
- **修复**：测试里 `sleep(0.05)` 跨 tick，断言改为 `>=`。
- **教训**：**时间相关断言不要假设单调递增**；生产代码里的租约窗口（60s）远大于时钟粒度，不受影响。

### 问题 2：任务 `DONE` 了，但 `current_stage` 还停在 `QC`

- **现象**：`test_full_pipeline_reaches_done` 断言 `current_stage is None` 失败，实际是 `'QC'`。
- **根因**：`_advance()` 在最后一个阶段只调用 `finish(DONE)`，没有清空 `current_stage`。
- **修复**：终态前显式 `UPDATE tasks SET current_stage = NULL`。
- **教训**：**"终态"是一个状态，不是一堆字段的默认值**。前端的进度条、恢复逻辑都依赖这个字段，脏值会静默传染。

### 问题 3：并发测试"假死"——子进程写错了库

- **现象**：`test_two_workers` 跑满 90s 超时，任务永远停在 `PENDING`。
- **根因**：子进程用 `Settings()` 读环境变量，`db_path` 落回默认 `./app.db`，而父进程在 `tmp_path` 里建的任务。
- **修复**：子进程 env 注入 `DB_PATH / ARTIFACTS_DIR / FAKE_STAGE_SLEEP / POLL_SEC`。
- **教训**：**进程级测试必须显式传递配置**。这也正是"配置收口"的价值——改一行 env 就能隔离。
