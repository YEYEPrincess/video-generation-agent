# ADR-0001：为什么用「7 阶段状态机」而不是「一条长 prompt」

- 状态：已采纳
- 日期：2026-10-25

## 背景

文本 → 分镜 → 素材 → 配音 → 渲染，天然是多步骤。有两种极端做法：

1. **一条长 prompt + 一次模型调用**，让模型直接吐出"完整方案"，再由代码渲染；
2. **拆成 7 个阶段**，每段有独立输入/输出契约和校验器，落库、可重跑。

## 决策

选择 2：7 阶段状态机，`current_stage` 落库，每阶段产物独立落盘。

## 理由

| 维度 | 一条长 prompt | 7 阶段状态机 |
|---|---|---|
| 失败定位 | 只能整段重来 | 定位到具体阶段/镜头 |
| 成本 | 一次大调用，改一个字也要全量重跑 | 命中幂等即跳过，改素材不重跑配音 |
| 可测性 | 输出是一个大 JSON，没法单测 | 每段契约 + 校验器可单测 |
| 可恢复 | 进程一挂全丢 | 断点续跑（M4 已验证） |
| 可观测 | 只有一个总耗时 | 每阶段耗时/token/成本 |

## 代价

- 阶段之间要维护产物契约（见 `app/contracts.py`），改字段要同步上下游；
- 阶段数变多，`current_stage` 推进逻辑要单独测试。

## 结论

在"会失败、要重试、要计费"的真实场景里，**可恢复性比调用次数更重要**。
一次调用看起来便宜，但一次失败就要从头再来，实际更贵。
